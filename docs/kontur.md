# Контур: единый интерфейс задач и агентской работы

Контур использует существующие карточки Todo, их постоянные ID, Markdown/YAML,
версии и авторизацию. Дополнительная база задач не создаётся.

## Принцип простоты

Контур следует правилу **«один смысл — одно название — одно место»**.
Основной путь должен быть понятен без знания внутренней модели данных:

- **«Дедлайн»** — крайнее время, когда нужен результат (поле dueAt).
- **«Когда начать»** — необязательный план начала работы (поле scheduledAt),
  а не второй дедлайн.
- Если известен только дедлайн, заполняется «Дедлайн». Если известен только
  план начала, заполняется «Когда начать». Одно значение не копируется в оба поля.
- Второстепенные параметры скрываются в разделе «Дополнительно». Они не должны
  конкурировать с названием задачи, исполнителем, состоянием и датой готовности.
- Интерфейс не показывает два разных понятия одинаковыми словами. Новая функция
  считается удачной только тогда, когда она уменьшает число решений пользователя.


## Представления

Основной экран `/` содержит ежедневную сводку, Kanban, список, календарь,
связанные сессии, блокеры, ссылки на PR и выкладки, действия и решения.
`/kontur` открывает тот же экран. `/classic` сохраняет прежние представления
доски, включая расширенное планирование.

Семь основных разделов навигации доступны всегда: Airlock, ex-менеджер,
Agent Herder, GrepMesh, OpenCodex/OCX, User.IO и Vibe MCP. Это группы для просмотра,
а не новые проекты в хранилище. Явные варианты названий группируются только
при отображении. Реальные имена и ID проектов, карточек и сессий сохраняются.
Отдельный список «Имена из доски» и фильтр проекта используют исходные имена
из доступных пользователю данных и реестра проектов.

Фильтры по проекту, машине, статусу задачи, приоритету и типу записи работают
совместно с поиском. Типы: задача, сессия, PR, выкладка, решение и действие.
Выбор типа открывает соответствующее представление. В других представлениях
остаются связанные родительские карточки и их записи. Фильтры PR и выкладки
показывают только соответствующие ссылки; ссылка на релиз не считается
доказательством выкладки. Раздел навигации, точное имя проекта, тип записи
и вкладка сессий сохраняются в URL как `section`, `project`, `recordType`
и `sessionState`. Переход по ссылке восстанавливает эти параметры.

Пустые поля показываются как «неизвестно». Даты календаря отображаются по Москве.
Поле «Дедлайн» и связанное событие Keeper редактируются через штатную карточку. Поле «Когда начать» остаётся отдельным планом начала работы.

## Работа агента

В карточке расположен существующий блок управления исполнением.
Создание и продолжение сессии используют native execution API доски,
сохранённую операцию и её идентификатор. Неопределённый исход не создаёт
повторную сессию автоматически. Вопрос и ответ остаются привязаны к задаче.

Общий список сессий показывает сохранённые квитанции и время их обновления.
Он не подтверждает доступность машины или текущую активность процесса.
Владелец и приоритет сессии берутся из связанной карточки по её постоянному ID.
Вкладки активных, ожидающих и неизвестных сессий используют результат явной
проверки, если он получен, либо последнее сохранённое состояние. Эти источники
показаны отдельно. Давность записи не используется как признак зависания.

Кнопка «Проверить состояние» выполняет только чтение через
`GET /api/kanban/cards/:id/execution?session=status&operationId=...`.
Ответ должен соответствовать выбранным ID карточки, операции и сессии.
Для подтверждённого состояния нужны источник `agent-herder:agent_info`
и время проверки. Ошибки доступа, транспорта и некорректные ответы оставляют
состояние неизвестным. Проверка не вызывает `sync-result`, не запускает
и не продолжает агента, не меняет карточку. Результат чтения остаётся в открытом
интерфейсе; после перезагрузки или изменения версии карточки нужна новая проверка.
Источник не предоставляет подтверждённое состояние `stalled`, поэтому вкладка
«Зависшие» прямо сообщает, что наличие таких сессий неизвестно.

Открытая ссылка на PR или выкладку также не подтверждает merge или успешный релиз.
Состояние таких внешних результатов остаётся неизвестным до отдельной проверки.

## Ручная приёмка

В интерфейсе Контур завершение требует описания проверенного результата,
доказательства и явного подтверждения человека. Запрос проходит существующую
проверку браузерной личности и права владельца, исполнителя или назначенного
проверяющего. Подтверждение не даёт дополнительных прав.

`POST /api/kanban/cards/:id/verify` получает только `expectedVersion`, `result`,
`evidence` и `confirmed: true`. Автор и время задаются сервером. Одна атомарная
запись с проверкой версии сохраняет завершение, решение и
`manual_result_verification` в существующей Markdown-карточке.
Повторное завершение закрытой задачи и устаревшая версия отклоняются.
Незавершённые цели, вопросы, история и описания остаются в каноническом хранилище.

## Ошибки и обновление

Ошибка входа, ACL, HTTP 429, HTML вместо JSON и недоступность сервера
не превращаются в пустую успешную доску. Экран показывает ошибку и время
последней успешной загрузки. Запрос, начавшийся до успешного изменения,
не откатывает интерфейс к старому снимку.

Тема выбирается явно, сохраняется в `kontur-theme` и использует `color-scheme`
с `only dark` или `only light`. Начальная тема тёмная, акценты фиолетовые и лаймовые.
Ссылки на сервисы доступны из шапки каждого представления и из сводки.
Адрес сайта и MCP endpoint показаны отдельными переходами:

| Сервис | Сайт | MCP |
| --- | --- | --- |
| Сообщения | `https://msg.bezrabotnyi.com` | `https://msg.bezrabotnyi.com/mcp` |
| Agent Herder | `https://agent.bezrabotnyi.com` | `https://agent.bezrabotnyi.com/mcp` |
| Airlock | `https://airlock.bezrabotnyi.com` | `https://airlock.bezrabotnyi.com/mcp` |
| GPTAdmin | `https://mcp.bezrabotnyi.com` | `https://mcp.bezrabotnyi.com/mcp` |

Доступ к ним регулируют сами сервисы. Наличие ссылки не подтверждает подключение,
доступность MCP или содержимое интеграции; неподтверждённые данные не подставляются.

## Проверка изменений

Новые проверки используют искусственные карточки и временные каталоги.
Реальные задачи, токены, auth state и runtime.env не входят в исходники,
тестовые данные, скриншоты или отчёты.

Перед выпуском нужны focused tests, TypeScript, production build и проверка
интерфейса. Выпуск должен сохранять текущий runtime, его mounts и лимиты,
проходить действующий release guard и проверяться по точному commit/image.

## Дополнительные гарантии приёмки и продолжения

Приёмка разрешена только с точного настроенного публичного origin или настроенного
origin включённого Airlock relay. Подмена `x-forwarded-*`, отсутствие Origin и
посторонний сайт не дают права завершать задачу.

Подтверждённый отказ Herder до создания сессии сохраняется в той же истории
как `stopped` без выдуманного session ID. Для этого нужен точный receipt
`not_attempted` для уже записанного create intent. Неизвестный исход и
подтверждённый запуск нельзя заменить таким отказом. После доказанного отказа
незавершённая цель и source intent сохраняются для осознанного продолжения.
